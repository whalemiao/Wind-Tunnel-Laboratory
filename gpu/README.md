# GPU 求解器（WebGL2）

把求解器从 CPU 搬到 GPU。参考
[PavelDoGreat/WebGL-Fluid-Simulation](https://github.com/PavelDoGreat/WebGL-Fluid-Simulation)（MIT）
与 [GPU Gems Ch.38](https://developer.nvidia.com/gpugems/gpugems/part-vi-beyond-triangles/chapter-38-fast-fluid-dynamics-simulation-gpu)。

## 现在能跑的部分

**求解器**：WebGL2 + 浮点渲染目标（RGBA16F / RG16F / R16F），8 个物理着色器
（速度对流 / 散度 / Jacobi 压力 / 减梯度 / 涡量约束 / 染料对流 / 入口注入 / 初始灌流）。

## 交接单第一件「条纹不流动」：结论是**没有这个 bug**

上一轮写的是「染料只出现在入口左侧 2%，但 `?wide=1&probe=1` 读回 `dyeMid=0.972`，两者矛盾」。
现在用确定性探针跑完，结论是**两个读数都不可靠，求解器本身是好的**：

| 证据 | 数字 |
| --- | --- |
| 染料前沿位置跟随 `u·t` | t=1.08s 前沿≈0.55、t=2.0s ≈0.87；实测速度 (0.87−0.55)/(2.0−1.08)=**0.348**，正好等于 u=0.35 |
| 速度场均匀 | `u@x=[0.35 0.35 0.34 0.34 … 0.34 0.35]`，全场平 |
| 散度压干净 | `divMid≈0.0000`（投影正常） |
| 染料整场剖面 | `dye[1.00 1.00 0.99 … 0.93 0.87 0.45 0.04]`（`?wide=1&warm=120`） |

两个「证据」为什么骗人：

1. **探针只采了 y=0.5 这一行**，而条纹注入是 `step(0.5, fract(vUv.y*14.0))`，
   `fract(0.5*14)=0` —— y=0.5 恰好落在两条亮带之间的暗带上，那一行**永远是 0.00**。
   `?wide=1` 绕过条纹函数把左侧 20% 全填 1.0，所以它读得到 0.97。两回事。
2. **无头浏览器不驱动 requestAnimationFrame**。`--virtual-time-budget=5000 --screenshot`
   拍到的其实是 t≈0.03 的那一帧（HUD 实测 `t=0.07`，只跑了 4 帧），
   染料当然还在入口那 2% 里。这不是模拟不流动，是截图太早。

修法不是改着色器，是**把验证手段修好**：加 `?warm=N`，渲染前同步跑 N 个定步长帧。
`?warm=360` 出来的就是 t=6.00 的稳态场（见 `shots/gpu-stripes.png`）。

## 实现要点（移植时踩到的）

### 三层显示

- 场 / 烟 都只有一次全屏 pass，纹理都是现成的
- 速度、压强、涡量用**自动对比度**：每 0.25 s 在 11×11 的粗网格上 `readPixels` 取 max
  （121 次 1×1 读，开销可忽略），再喂给色标
- **发散色标的零点不能是白色**：一开始写成「负→蓝、正→白黄」，结果涡量整屏发白；
  照抄 CPU 版 `diverging()`（暗蓝 → 中蓝 → 亮黄白）后才有层次

### 流线（GPU 上怎么画）

流线要「沿一条线积分几十步」，GPU 得为每个顶点重复积分，不划算。做法：

1. 每 0.2 s 用一次 `readPixels` 读回整张速度场（S²）
2. 空间平滑（S/128 半径）+ 时间低通（0.85 旧 / 0.15 新）—— 不平滑线会像闪电一样抽
3. JS 里 RK2 积分：步长 0.55 格，每步限转角 0.1 rad，**撞到固体格立刻断线**
4. 积分结果缓存到离屏层，8 Hz 重建，每帧只 `drawImage` 一次（否则 60fps 扛不住）

坐标映射：横屏 `px = fx·W, py = fy·H`；竖屏 `px = (1−fy)·W, py = (1−fx)·H`，
和显示 pass 的 `fuv` 旋转完全一致（否则竖屏里流线会和烟错位）。

### 画笔 / 手画层

`paint` 是一个 `Uint8Array(S²)`，`uploadMask()` 里 `if (paint[i]) a = 1` 并进固体掩码；
橡皮就是写 0。整张掩码每次重算（S² 循环 + `getImageData`），512² 下拖动会有十几毫秒，
和 CPU 版同一个量级。

### 物体为什么清楚（那条"糊"的坑）

一开始物体颜色是按**网格分辨率**（256×150）上传的，放大到屏幕上就被双线性插值糊掉了。
现在分两张贴图：

- `solid`（R8，网格分辨率）—— 只管物理：哪一格是墙
- `maskColor`（RGBA8，**网格 × MK**，MK = 1~4，按画布像素算）—— 只管好看：原图直接画上去，
  不在中间缩一次（和 CPU 版的原则一样）

白边也改成看 `maskColor.a` 的平滑过渡（`rim = 1 - smoothstep(0.6, 0.98, a)`）：
按网格掩码描边会是一圈格子锯齿。

### 出口边界：为什么从"硬吹"改成"压力出口"

最早两端都硬吹 `v=(inflow,0)`：稳定、但物理错 —— 等于在出口也往场里灌质量，
所以尾流里会出现**回流**（实测 `u=-0.25`），压力还有一条贯穿全场的假斜坡
（这是投影在替这个假边界"还债"）。

现在（默认 `?outlet=nrbc`）：

- 速度：出口用零梯度外推（`v(out) = v(out-1)`），让 outgoing 特征自由离开
- 压力：出口给 Dirichlet `p=0` —— 有了"压力出口"，速度那边才敢不硬吹

对比（`?preset=car2&py=0.62&warm=600`）：

| | 旧（hard + 0.994） | 新（nrbc + 1.0） |
| --- | --- | --- |
| 尾流 u | 0.12 → 0.16，中间还夹着 **-0.25** | 0.25 → 0.31 单调恢复 |
| 尾流 p | 0.17 → 0.01 的全局斜坡 | 贴 0（±0.02） |
| 20s 长跑 | — | 稳定，不发散 |

**顺带揪出的真凶**：默认 `vdis=0.994` 意味着每帧 ×0.994（60 帧掉 30% 速度）。
旧边界靠"两端硬吹"一直在补这个损耗，所以换了出口就"掉速" —— 一开始以为是边界写错了。
现在默认 `1.0`，黏性滑杆（0~100）才是唯一的阻尼旋钮。

### 手机手势（触摸 ≠ 鼠标）

同一个 `pointerdown/move/up` 监听器里分三条路：

1. **单指**：和鼠标一样按 `toGrid()` 位移搬物体，或者（选了画笔时）涂抹
2. **双指**：按下第二根手指就切到捏合 —— 用两指距离算 `objScale`、两指夹角算 `objAngle`，
   松开任意一根就结束（`activePtr.size < 2`）
3. **双击**：手机没有 `dblclick`，自己判两次轻点（320ms 内、位移 < 12px、间距 < 40px）

两个坑：

- **`touch-action: none` 是前提**。不写的话手指一拖，浏览器把 `pointermove` 当成滚动吞掉，
  还会立刻发 `pointercancel` —— 现象是"手机上手势完全没反应"，但鼠标一切正常
- **`pointercancel` 要兜底**：来电、从屏幕边缘返回、下拉通知都会打断，不重置状态就会
  卡在"一直拖动"

### 分辨率原地重建

`S` 是 `let`，`allocTargets()` 负责删旧纹理、建新纹理、重绑 ping-pong 变量。
图片和手画层都留在内存里，所以换分辨率不会「变回默认形状」（CPU 版当年也踩过这个坑）。

## 性能

软件光栅（swiftshader）下 256² 带流线约 49fps、带粒子 62fps（`?drive=timer` 实测）；
真实 GPU 会高一个量级。这正是把求解器搬到 GPU 的原因：CPU 版 320×180 已经 20-40fps。

把「会掉帧的东西」都改成按需 / 降采样之后，每帧的固定开销只剩：物理 pass + 一次显示 pass +
（流线开着时）8Hz 的画布重建。具体抠掉的：

| 原来 | 现在 |
| --- | --- |
| 每 0.25s 240 次 `readPixels` 求量程 | 只在「场」显示时采样，5×5 网格、0.5s 一次 |
| 流线读回 S²（512² = 4MB） | 先 blit 到 160² 再读（100KB） |
| 平滑 O(25·S²) | 可分离盒滤波 O(2·S²)，且跑在 160² 上 |
| 每帧 clear + drawImage 2K 覆盖层 | 只在重建时更新 |
| pointermove 每次都重建掩码 | 一帧最多重建一次 |
| 画布按 dpr 2.0 分配 | 上限 1.5（满屏填充少 44%） |
| 手机上也用 512² | 窄屏默认 256²（`?sim=` 可覆盖） |

## 已知坑（别再踩）

| 坑 | 教训 |
| --- | --- |
| 用 `idx = 1 - idx` 翻转计数做 ping-pong | 改成显式 `read`/`write` 变量；翻转次数错一次就绑到空纹理，且不报错 |
| 改 shader 的 `uniform` 声明用字符串替换 | 容易插错 shader（把 `uInflow` 插进 pressure 而不是 gradient，整页白屏） |
| 入口速度 | 必须启动时把整场灌成均匀来流；半拉格朗日自对流不会把速度"扩散"出去 |
| 画布尺寸变化后 | 要重新验证染料对流：`dt` 与 UV 单位的比例变了 |
| **无头浏览器不跑 rAF** | `--virtual-time-budget` 只推进定时器；截图前必须 `?warm=N`，否则拍到的是第 4 帧 |
| **探针只采一行** | y=0.5 正好落在条纹暗带上，会读到"整场全 0"；改读整行 + `?grid=1` |
| 出口改零梯度 | 试过：`u` 从 0.35 沿程掉到 0.20，全场速度塌掉；保持两端 Dirichlet 吹入 |
| 粒子寿命全一样 | 会同步重生形成"粒子浪"；寿命乘以个体随机数 |
| 竖屏时给物体补 90° | 车会横过来变成一堵墙，把风道堵死（CPU 版也踩过）。竖屏是「画面整体转 90°」，不是「物体转 90°」——物体的长轴要始终顺着风 |
| **画布 y 向下、纹理 y 向上** | 一个约定错，三个症状：导入的图**倒立**、拖动方向**反**、画笔**落点跑偏**。修法：上传时整行翻转（`out[fy*S+x]`）、物体中心画在 `SY·(1−objY)`、指针一律走 `toGrid()` 换算，别再另写一套 dx/dy |
| 场是正方形、画布不是 | 整个场被拉成画布比例 = 物体"变形"。现在场按画布比例走：`S×SY`，`SY = S × 画布高/宽`（竖屏反过来），`?sim=` 只是**宽度** |
| `toGrid()` 的 y 乘了场宽 | 场变成长方形后，y 要乘**场高** `SY`。这条错的时候，笔画总是落在指针**上方**（偏移量 = S/SY 倍） |
| 素材本身是倒的 | `presets/car2.png` 当年存反了（轮拱朝上）。修渲染的同时把它翻正，否则"修好了反而看着倒" |
| 流线没判固体 | 线会直接画穿车身；积分每一步都要查 `solidBits`，种子点也要跳过 |
| 发散色标零点用白色 | 涡量/压强整屏发白，看不出结构；零点必须是中性色 |
| 脉线（GL 画的）没套竖屏旋转 | 烟和流线在显示 pass 里转了 90°，脉线却是原样画到画布上的 → 竖屏里它比别的层拧 90°。`VS_STREAKS` 里必须做同一个 `uv = (1−p.y, p.x)` 变换 |
| `readPixels` 用得没节制 | 它是同步的，一次就 stall 整条管线。之前 `sampleMaxima()` 无条件每 0.25s 做 240 次 1×1 读 → 每秒掉几十毫秒。现在：只在「场」显示时才采样、5×5 网格、0.5s 一次 |
| 流线读回整张速度场 | 512² = 4MB，读一次就卡一下；改成先 blit 到 160² 的 `velSmall` 再读（100KB，40 倍便宜） |
| 平滑写成 O(25n) | 512² 上每次 6.5M 次采样，每 0.2s 一顿；换成可分离的一维盒滤波，O(2n) |
| 每帧 clear + drawImage 覆盖层 | 2K 画布每帧贴一次纯属白花；改成只在流线重建时更新覆盖层 |
| 指针事件里直接重建掩码 | 120Hz 的 pointermove 每次都跑 S² 循环 → 画笔拖起来就卡；改成一帧最多重建一次（`pendingStamps`） |
